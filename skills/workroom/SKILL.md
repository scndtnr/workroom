# workroom の確認事項

workroom の部屋は `YYYY-MM-DD-<名前>` のディレクトリで、README.md と AGENTS.md がある（例：`~/work/2026-11-03-調査`）。
ユーザーは、エージェントが起票した質問を成果物ハブ（`workroom hub` で開くブラウザの画面）で読み、回答する。質問と回答は、部屋の `QUESTIONS.jsonl`・`ANSWERS.jsonl` に記録される。

- 部屋の AGENTS.md の「確認事項」の節が、必須の手順。このスキルは、その書き方と流れを詳しくしたもので、決まりは同じ。
- 引数とオプションの細部は、`workroom q --help` と `workroom q <コマンド> --help` で確かめる。
- 部屋の外から実行するときは、`--room <部屋の名前>` を付ける。

## いつ起票するか
- その場で一言で答えられない質問を起票する（方針の選択、ユーザーに調べてもらうこと、後で答えたいもの）。一言で答えられるものは、会話でそのまま聞く。
- 起票したら、出力された ID（例：`Q-20261103-01`）をユーザーにも伝える。
- 作業を始めるときは、`workroom q pending` で、反映を待っている回答がないかを確かめる。

## 質問の書き方
- 質問は1〜3行の要点にする。経緯・調べたこと・選択肢ごとの影響などの詳細は `--background` に書く。
- `--by` には、役割の分かる名前を付ける（例：`--by '調査担当（Codex）'`）。並列で作業しているときに、どのエージェントの質問かをユーザーが見分けられるようにする。
- 選択肢があれば `--choice` を繰り返し、勧めるものを `--recommend <番号>`（1 から）で示す。
- URL と他の文字の間には、半角スペースを入れる。URL の直後に空白なしで記号や日本語を書くと、それも URL に含まれる。
- ファイルパスはバッククォートで囲む（例：`` `docs/plan.md` ``）。ハブでリンクとインラインコードになる。囲まないと、直後の日本語までパスに含まれることがある。部屋の中のファイルは、部屋からの相対パスで書く。

### 改行の渡し方
質問と背景には、実際の改行を渡す。コマンドラインに書いた `\n` の2文字は改行にならず、そのまま保存される（`workroom q ask` が警告を出す）。

**単引用符の中で、実際に改行する。** PowerShell・bash・nushell で同じ書き方が使え、バッククォート・`$`・`\` もそのまま渡る。

```
workroom q ask '設計の案A と案B のどちらで進めますか。
比べた結果は `docs/plan.md` にまとめました。' --background '案A は既存の形式を保てる。
案B は速いが、移行が要る。' --choice '案A' --choice '案B' --recommend 1 --by '実装担当（Claude Code）'
```

- 二重引用符は使わない。PowerShell ではバッククォートがエスケープ文字になり、`` `n `` が改行に化ける。bash ではバッククォートと `$` が展開される。nushell では `\n` が改行になり、Windows のパスが壊れる。
- 文の中に単引用符（`'`）を入れるときは、次の書き方にする。
  - PowerShell：`''` と2つ重ねる。または here-string `@'` … `'@`（閉じる `'@` は行頭に置く）。
  - bash：`"$(cat <<'EOF'` の次の行から本文を書き、`EOF` の行の後に `)"` で閉じる。
  - nushell：`r#'` … `'#`。

## 回答を受けたとき
1. 次のときに `workroom q pending` を実行する。
   - 作業を始めるとき
   - ユーザーが「回答した」と言ったとき
   - ハブの貼り付け用の文を受け取ったとき
2. 表示された回答を、README.md や計画の文書など、部屋の中の適切な場所に反映する。
3. 出力に示された `workroom q done <ID> --upto <n> --to '<反映先>'` を、そのまま実行する。
   - `--upto` の番号は変えない。`pending` を読んだ後に届いた回答を、読まずに反映済みにしないため。
   - `--to` には、反映した場所を書く。パスはバッククォートで囲む（例：`` --to '`README.md` の「方針」' ``）。
   - 回答不要と答えられた質問は、`--to` を省ける（出力の実行例もそうなっている）。
4. 会話で回答を受けたときは、`workroom q done <ID> --chat '<回答の要旨>' --to '<反映先>'` で記録する。

## 聞き直し・取り下げ
- 質問を直して聞き直すときは、先に新しい質問を起票し、次に古い質問を取り下げる。
  1. `workroom q ask '<直した質問>' --origin <旧ID> --by '<名前>'`（新しい ID が出る）
  2. `workroom q withdraw <旧ID> --reason '<理由>' --successor <新ID>`
- 質問が要らなくなったら、`workroom q withdraw <ID> --reason '<理由>'` で取り下げる。
- 取り下げた質問の回答を反映済みの場所があれば、出力に一覧が出る。取り下げに合わせて見直す。

## 並列で作業するとき
- `workroom q ask`・`workroom q done`・`workroom q withdraw` を実行するのは、ユーザーと話しているエージェントだけにする（部屋の AGENTS.md と同じ決まり）。
- ほかのエージェントは、質問の案（質問・背景・選択肢）を、ユーザーと話しているエージェントに渡す。`workroom q pending`・`workroom q show` で読むのはよい。

## してはいけないこと
- `QUESTIONS.jsonl`・`ANSWERS.jsonl` を手で書く・直す・消すこと。記録は workroom のコマンドだけで書く。
- `pending` の実行例の `--upto` を書き換えること。

## コマンドの早見表
| コマンド | 使う場面 |
|---|---|
| `workroom q ask '<質問>' --background '<詳細>' --by '<名前>'` | 質問を起票する。標準出力は ID だけ |
| `workroom q pending` | 反映が要る回答と、未回答の件数・ID を見る（`--json` もある） |
| `workroom q done <ID> --upto <n> --to '<反映先>'` | 回答の反映を記録する（`pending` の実行例を使う） |
| `workroom q withdraw <ID> --reason '<理由>'` | 無効になった質問を取り下げる |
| `workroom q show` | 未回答・未反映の質問と回答の全文を見る（`--all` で解決済みも） |
